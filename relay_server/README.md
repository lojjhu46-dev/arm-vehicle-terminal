# relay_server — Windows 公网中继服务（UDP → 帧感知单槽 + 发完整帧 + 主动限速 → WebSocket）

接收开发板（camera_project）发来的 **UDP 8888 分片**（原 1324B 协议），先组帧、再按
**"帧感知单槽 + 发完整帧 + 主动限速"**策略经 WebSocket 广播给公网客户端，保证公网端
看到的始终是**最近**的完整画面，且协议格式与原 Android app 完全一致。

> 因 cpolar 为 HTTP 隧道无法透传裸 UDP，故用 WebSocket 逐包封装。
> 每个 WS 二进制消息 = 一个原始 1324B 分片。

## 数据流向

```
开发板(ARM) --UDP 8888 分片--> relay_server(本服务) --WebSocket binary 逐片--> cpolar HTTP隧道 --> 公网接收程序
```

## 为什么用"发完整帧 + 主动限速"（限速下的延迟优化）

免费版 cpolar 隧道带宽约 **1Mbps（≈128KB/s）**，而开发板 30fps、640×480 q55 JPEG
每帧 30-60KB，约产生 **1-2MB/s** 数据，远超隧道吞吐。

### 演进教训一：被动打断不可靠

早期方案依赖 `ws.send()` 阻塞产生背压来触发"打断"——但 cpolar 的 1Mbps 限速发生在
**公网侧（隧道内部）**，中继写本地 socket 发送缓冲几乎从不阻塞。结果所有帧瞬间进入
缓冲、在隧道内排队积压，延迟依然累积，日志中"丢弃(打断)"几乎为 0。

### 演进教训二："新帧立即打断旧帧"导致半帧饥饿

后来改为主动限速（令牌桶）+ 新帧到达即打断旧帧。但打断太频繁时，接收端长期处于
"组半帧→被打断→切新帧"状态，**很久收不到一个完整帧**，显示的仍是几秒前偶然完整的
旧帧——**延迟反而高达 5 秒**。

### 最终方案：发完整帧 + 按帧漏桶限速

中继发送一帧时**发完所有分片**，不因新帧到达而打断；发送期间到达的新帧仅覆盖帧槽
（自然丢弃旧帧）。发完当前帧后，取帧槽中**最新**的帧再发。限速采用**按帧漏桶**
（每发完一帧补齐该帧的时间预算，sleep 次数少、调度误差小，实际速率贴近且**不超过**
`--max-kbps`，不再有令牌桶的突发超发）。

效果（实测）：

- 接收端每次稳定收到**完整近期帧**，不再半帧饥饿；
- **延迟从 5 秒降至约 0.6 秒**（= 一帧传输时间 + 帧槽停留 + 网络 RTT），不再随时间累积；
- **实际发送速率恒 ≤ 限速**，不会因瞬时突发在隧道内积压；
- 丢帧通过"帧槽覆盖"自然发生（发送期间到达的旧帧未发出即被新帧覆盖）；
- 发送侧使用**连续帧号**（取最新帧内容，但 frame_id 自增连续），保证接收端"帧号连续"
  检查全部通过、每帧都能组上。

## 协议兼容性

- 仍为固定 **1324B/包**（24B 小端帧头 + 1300B 负载，尾片零填充），校验和算法不变；
- 中继**发送侧自增连续帧号**：取帧槽最新帧内容，但 frame_id 始终连续递增，接收端
  "帧号连续"检查不会误触发；
- 接收端（public_viewer / Android app）**零改动兼容**。

## 依赖安装（原生 Windows Python 3）

```bat
py -m pip install -r requirements.txt
```

仅依赖 `websockets`。

## 启动

```bat
py relay_server.py --udp-port 8888 --ws-port 8080
```

参数（均可省略，用默认值）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--udp-port` | `8888` | UDP 接收端口，需与开发板发送端口一致 |
| `--ws-port` | `8080` | WebSocket 端口，**cpolar 隧道指向此处** |
| `--host` | `0.0.0.0` | WebSocket 绑定地址 |
| `--max-kbps` | `80` | **主动限速带宽(KB/s)**，默认 80≈0.62Mbps，低于免费版 cpolar 实测吞吐，避免积压 |
| `--log-level` | `INFO` | 日志级别 |

启动后应看到：

```
UDP 监听 0.0.0.0:8888
WebSocket 服务 ws://0.0.0.0:8080（供 cpolar 指向）
```

## 与 cpolar 对接

1. cpolar 用 **HTTP 隧道**，指向 `http://localhost:8080`（即 `--ws-port`）。
2. 启动本服务后，公网 URL（如 `http://214006ed.r27.cpolar.top`）即暴露 WebSocket 端点，
   客户端以 `ws://214006ed.r27.cpolar.top` 连接。

## 日志说明（每 5s 一行）

```
收包 1300/s | 无效包 0 | 组帧 30 | 发送帧 4 | 丢弃(打断) 26 | 实际发送 100 KB/s | 客户端 1
```

- `组帧`：中继组出的完整帧数（输入帧率）；
- `发送帧`：实际发完整帧并广播的帧数（输出帧率，多客户端时累计）；
- `丢弃`：= 组帧 - 发送帧，即发送期间被帧槽覆盖而**未发出的旧帧**数——**>0 是正常的，
  说明限速节流生效、旧帧被主动丢弃而非积压**；
- `实际发送`：本周期实际发送字节速率，应接近 `--max-kbps` 设定值。

**如何判断调优是否到位**：若 `实际发送` 长期 **接近** `--max-kbps` 且 `丢弃`>0，
说明中继正在按限速丢弃旧帧、延迟不累积；若 `实际发送` 长期**低于**限速但 `丢弃`=0，
说明生产速率本就不足（无需担心）或 `--max-kbps` 设置过高。

## --max-kbps 调优方法

`--max-kbps` 应**低于** cpolar 隧道实际可用带宽：

- 免费版 cpolar 名义 1Mbps = 125KB/s，实测常打折（80~100KB/s）→ 默认 `80` 较稳妥；
- 若用付费版/更高带宽，先实测隧道实际吞吐（`实际发送` 日志），再按 `实际吞吐 × 0.7~0.8` 设置；
- 设置过高 → 数据在隧道内积压，延迟重新累积；设置过低 → 帧率被无谓压低。

> 漏桶保证实际发送**恒 ≤ `--max-kbps`**：若日志中 `实际发送` 长期低于限速，
> 说明生产速率不足或限速值偏高，可适当调低限速避免无谓积压。

## 带宽与帧率的关系（参考）

| 带宽 | 30KB/帧 | 60KB/帧 |
|---|---|---|
| 1Mbps (128KB/s) | ~4 fps | ~2 fps |
| 2Mbps (256KB/s) | ~8 fps | ~4 fps |

## 前置条件

- 开发板发送目标 IP 已改为**本机局域网 IP**（见 `camera_project` README）。
- 开发板与运行本服务的 Windows 主机在**同一网段**。
- 若本机 UDP 8888 被占用，换端口并用 `--udp-port` 指定，同时改开发板端 `PORT`。

## 联调验证

1. 先启动本服务。
2. 用任意 WebSocket 客户端连接 `ws://127.0.0.1:8080`（或公网地址）。
3. 启动开发板采集发送，客户端应立即收到连续 **1324B** 二进制分片，`无效包` 应为 0。

## 部署注意（重要）

- **升级后必须重启中继**，并让接收端重连一次：之前积压在隧道/发送缓冲中的旧数据
  必须被消费完，否则延迟可能残留到重启后的一段时间。

## 可选：降低开发板码率（提升帧率）

若希望牺牲画质换更高帧率，可改开发板 `frame.c` 中 `jpeg_set_quality(&cinfo, 55, TRUE)`
的 `55` 为更低值（如 `30`），或降低采集帧率（`mainloop` 中 select 超时后仍立即取帧，
可在 `tv.tv_usec` 处增加等待）。**注意**：这是开发板端可选项，非本次链路必须。
